## 1. Executive summary

RIMWAKE is a working scientific web experience that helps people understand how a change in lunar location or mission date changes the modeled Sun and Earth conditions over an observation window. Its central interaction is a comparison: choose two documented lunar viewpoints, inspect an original mission window, move the same window later, and examine what changes.

The project combines authentic archived NASA/JPL ephemerides with a cinematic explanation and an interactive geographic workspace. The landing experience introduces the question through six scroll chapters. The Explorer connects a lunar globe, signed sky chart, original/delayed summaries, exact UTC readings, and timeline tracks. Every scientific view uses the same active source sample.

The current atlas contains **25,932 hourly body/site readings**, covering **six documented locations**, **two bodies**, and **90 days**. NASA NSSDCA provides the source landing coordinates. JPL Horizons provides apparent airless azimuth and elevation for hypothetical observers at those coordinates. These are computational ephemerides, not telemetry measured by the historical landers.

The project preserves the original scientific release and its legacy observations. The newer six-site archive is a separate release with its own identity, manifests, raw responses, and source records. Scientific values are not generated by AI. The accepted brand concept was created with AI image generation and reconstructed as a lightweight production SVG.

The latest recorded verification includes **43 TypeScript unit tests, 39 Python scientific tests, and 62 production browser tests**, all passing. Multiple screenshot iterations informed refinements to the phone hierarchy, chart text, comparison visibility, and globe labels. An owner-reported Globe → Sky → Globe regression was reproduced, fixed, and covered by new desktop and phone tests.

RIMWAKE is a completed local hackathon prototype with a substantial working interaction, rather than a visual mockup. It is not a certified mission-planning system. Independent ephemeris validation and exact source-frame reconciliation remain open. Terrain, power generation, RF performance, finite-disc effects, and eclipses are outside the current calculation. Some mobile performance targets also remain unmet.

## 2. Problem and hackathon objective

Lunar exploration involves questions that are spatial, temporal, and difficult to communicate through isolated numbers. A place can have favorable Sun geometry but unfavorable Earth geometry. A different place, or a different start date, can change the relationship. Understanding a single timestamp is useful, but understanding a whole window and a schedule change is more informative.

The original project problem therefore had two parts. First, make authentic scientific records understandable without asking a visitor to interpret an ephemeris table immediately. Second, turn those records into a meaningful comparison while preserving their assumptions and provenance.

For the NASA Space Apps hackathon context, the objective became:

> Build an engaging, source-traceable lunar exploration experience in which a visitor can understand a question, perform a comparison, inspect an exact result, and carry the evidence away.

The implemented prototype addresses geometric conditions above a defined reference horizon. It does not claim to solve operational landing-site selection. Real site selection also requires terrain, vehicle constraints, illumination of finite bodies, communications engineering, uncertainty analysis, and mission-specific requirements.

The current product deliberately answers a narrower question well: how do sampled Sun/Earth centre directions change across two hypothetical viewpoints and two equal-duration windows?

## 3. Project identity and meaning

### 3.1 Why RIMWAKE?

RIMWAKE is a coined name connecting two ideas:

- **Rim:** lunar crater rims and geography, which motivate the broader question of observing from the lunar surface.
- **Wake:** revealing the consequences of changing a place or observation window.

The name supports an exploration-instrument identity. Its connection to crater rims is conceptual: the current P0 implementation does not calculate obstruction by a crater rim. The name must not be interpreted as evidence that a terrain model has been validated.

### 3.2 Product language

The experience uses a direct narrative: **“The place. The date. The difference.”** The Explorer asks, **“What if the date changes?”** These statements express an action the visitor can actually perform.

Terms are chosen to preserve meaning. A “viewpoint” is a hypothetical observer; “above horizon” refers to the defined geometric plane; a “sample” is an archived hourly record; and a “delay” shifts the original window without silently changing its duration. Scientific uncertainty and numerical precision remain distinct.

### 3.3 Accepted logo

The approved mark combines an open circular rim, a rising diagonal horizon, a subtle negative-space R, and one restrained amber segment. The mark suggests emergence and an observation opening. Lunar white connects it to the surface; amber connects it to the Sun.

The accepted transparent raster is preserved at **1254 × 1254 pixels**, with RGBA transparency. It is **512,534 bytes**. A reconstructed native SVG of **474 bytes** is used in the interface, with a dark variant and favicon. This retains a usable small-scale identity without loading the large source raster into every header.

## 7. Explorer functionality and interaction

### 7.1 Configuring a comparison

The visitor assigns viewpoints A and B from six documented locations, selects an exact supported UTC start, chooses a duration, and specifies a schedule slip. Presets offer 1, 3, 7, and 14 Earth days. Custom durations support **24–336 whole hours**. Delays support **0–336 whole hours**.

Both the original and delayed windows must fit the archive. Unsupported starts, invalid ranges, and out-of-window cursors produce an explanation. The application does not invent an ephemeris to satisfy an unsupported input.

### 7.2 Comparing outcomes

Each location has original and delayed summaries for Sun above, Earth above, and both above. The interface presents sample shares, sample counts, sampled runs, and explanatory differences. The core result appears before the geographic context so visitors can identify what changed without first interpreting a globe.

Same-site comparisons and zero delay are supported. Equal percentages do not imply identical angles or timing. Incomplete scientific coverage suppresses a comparative verdict.

### 7.3 Inspecting a shared time

One request owns the active scenario and elapsed-hour cursor. Within the active scenario, A and B use the same absolute UTC. Switching from Original to Delayed retains the elapsed-hour position while changing the corresponding absolute UTC by the selected delay.

Original and delayed timeline tracks are aligned by **mission elapsed time**, not falsely presented as simultaneous absolute dates. Every track retains its actual start timestamp.

Controls include exact UTC selection, previous/next samples, discrete playback, timeline selection, condition filtering, zoom, and crossing-bracket navigation. An unavailable UTC is rejected; an explicit nearest-supported-sample option can be chosen. Numerical positions are never interpolated.

### 7.4 Geographic and sky views

Globe provides geographic context, site selection, A/B labels, focus movement, and camera reset. Sky provides a signed elevation-versus-bearing chart with exact numeric readings. Historical site images provide optional context, with explicit separation from selected-date lighting.

Phones emphasize one focused site and place secondary settings/catalogs behind deliberate expansion. Globe rotation is unlocked explicitly so normal page scrolling remains usable. A map/list and scientific charts remain available without 3D.

### 7.5 Evidence and export

The visitor can inspect source runs and limits, copy a reproducible link, download comparison JSON, download source-linked CSV, and print a comparison brief. Clipboard failure retains a manual-copy route. The scientific result therefore remains inspectable and portable beyond the visual session.

## 8. Scientific model and scope

### 8.1 Definition of the model

The implemented model is named `tangent_plane_center_airless`. It uses apparent airless directions to the centres of the Sun and Earth from hypothetical lunar observers.

Azimuth is measured clockwise from north: north 0°, east 90°, south 180°, west 270°. Elevation is signed relative to the plane perpendicular to local zenith. This plane is not a terrain skyline. These definitions correspond to the observer azimuth/elevation quantities documented in the [JPL Horizons manual](https://ssd.jpl.nasa.gov/horizons/manual.html).

Observers use documented horizontal coordinates and **0 km reference-ellipsoid height**. They do not reproduce a lander's actual antenna height, instrument orientation, terrain elevation, or operating condition.

### 8.2 Classification rules

Let `e` be elevation in degrees and `epsilon = 0.000001°`.

```text
Unknown:   record unavailable, invalid, null, or non-finite
Above:     e > epsilon
Below:     e < -epsilon
Boundary:  -epsilon <= e <= epsilon
```

The epsilon is a numerical classification tolerance. It is not a claim of physical angular accuracy.

The internal state key `blocked` means below the reference plane; it must not be read as terrain obstruction. Joint Sun/Earth state is unknown if either body is unknown, below if a known body is below, boundary if neither is below and at least one is at the numerical boundary, and above only when both are above. The implementation gives unknown precedence conservatively.

### 8.3 Window statistics

For duration `H` hours and hourly cadence, including both endpoints:

```text
Expected samples N = H + 1
Above share (%) = 100 × above sample count / N
Change (percentage points) = delayed share - original share
```

A seven-day window has 168 elapsed hours and **169 samples**. A run of 117 consecutive hourly samples spans 116 hours between its endpoints. A single sample spans zero hours. Unknown and non-above states break an above-horizon run.

These are sampled classifications. They do not prove uninterrupted availability between samples. Percentages are neither probabilities nor percentages of usable power or communications uptime.

### 8.4 Crossing interpretation

A change between adjacent known classifications produces a bracket between their UTCs. The atlas reports the bracket rather than inventing an exact crossing time. Brackets are sorted chronologically. Boundary transitions retain their actual state labels; they are not silently promoted to a physically precise sunrise or Earthrise.

### 8.5 Scientific limits

Current calculations exclude terrain obstruction, digital elevation models, finite angular discs, eclipse/occultation effects, array orientation, usable solar power, energy storage, antenna pointing, RF link budgets, and spacecraft operations.

Input catalog coordinates are described as DE421 mean-Earth/polar coordinates, while retained Horizons headers identify MEAN_ME (high precision), with DE441 source ephemerides. Exact frame reconciliation has not been independently completed. Source consistency checks do not replace independent astronomical-model validation.

The preparation pipeline retains raw response bytes, request parameters/URLs, retrieval records, source hashes, and released records. The read-only archive checker reparses every source response and compares every published reading. Hashes establish byte consistency within the package. They are not digital signatures and do not independently establish physical correctness or protect against a party replacing an entire trusted package.

## 10. Worked scientific example

The default comparison uses Odysseus and Athena for **14–21 November 2026**, then delays the same seven-day window by 72 hours to **17–24 November**. All boundaries are at 00:00 UTC.

At `2026-11-14T00:00:00Z`, the atlas records:

| Site | Body | Azimuth | Elevation | Classification |
|---|---|---:|---:|---|
| Odysseus | Sun | 124.995975070° | −4.126238884° | Below |

### 10.2 Original and delayed windows

| Site and condition | Original above samples | Original share | Delayed above samples | Delayed share |
|---|---:|---:|---:|---:|
| Odysseus, Sun | 117/169 | 69.2% | 169/169 | 100.0% |
| Odysseus, Earth | 169/169 | 100.0% | 169/169 | 100.0% |
| Odysseus, both | 117/169 | 69.2% | 169/169 | 100.0% |
| Athena, Sun | 169/169 | 100.0% | 169/169 | 100.0% |
| Athena, Earth | 165/169 | 97.6% | 169/169 | 100.0% |
| Athena, both | 165/169 | 97.6% | 169/169 | 100.0% |

Odysseus gains **52 jointly above-horizon samples**, or **30.8 percentage points**. Athena gains **4 samples**, or **2.4 percentage points**. Originally, Athena has 28.4 percentage points more jointly above-horizon samples than Odysseus. The delayed windows have equal joint sample shares, although their angles can still differ.

The original Odysseus Sun classification changes between **16 November 03:00 and 04:00 UTC**. Athena's original Earth classification changes between **14 November 03:00 and 04:00 UTC**. These are hourly brackets.

The longest original joint run spans 116 hours between 117 sample endpoints at Odysseus and 164 hours between 165 endpoints at Athena. Each delayed joint run spans 168 hours between 169 endpoints. These statements remain sampled geometry, not continuous usable sunlight or radio availability.

The example demonstrates the intended scientific interaction: a changed date produces an inspectable change in archived classifications. It does not establish that delaying a real mission would be operationally preferable.

### 11.3 Worker and scientific engine

The worker verifies the archive index, loads selected site bundles, checks hashes, validates records, and computes summaries. Site promises and parsed series are cached within the worker. Generation IDs allow the UI to reject stale results after rapid changes. A failed load clears the relevant worker cache for retry.

The pure analysis engine creates source lookup maps, original/delayed clocks, classifications, summary metrics, timeline tracks, exact inspection rows, explanations, and CSV output. Keeping this logic separate from rendering allows deterministic tests and prevents display geometry from becoming a second scientific calculator.

Request processing includes release/site identity, complete timestamp matrices, target/run membership, finite angle ranges, quality-state rules, and supported selection bounds. An unavailable record remains unknown, rather than becoming a zero-degree direction.

### 11.4 Build and hydration

The build typechecks, bundles, and prerenders static route HTML. The browser hydrates that markup. Explorer starts from a common loading shell and then selects the atlas or preserved legacy interface according to the URL, avoiding query-dependent server/client markup mismatch.

Static headings and explanatory content are tested with JavaScript disabled. Interactive scientific analysis still requires JavaScript and the worker. Without WebGL, the scientific controls and SVG/map alternatives remain usable; that is different from claiming a fully functional JavaScript-free application.

### 13.3 Motion and 3D

Motion is silent and purposeful: camera focus, scroll-linked storytelling, and restrained transitions. The atlas camera flight lasts approximately **750 ms**. Camera animation is a UI effect; numerical ephemerides do not interpolate during it.

The geographic transform uses latitude `phi`, east longitude `lambda`, and display radius `r`:

```text
x = r cos(phi) sin(lambda)
y = r sin(phi)
z = r cos(phi) cos(lambda)
```

Longitude zero faces +Z, east is +X, and north is +Y. The map texture is aligned to this convention. The display transform positions geographic context; it does not derive Sun/Earth ephemerides.

The globe renders on demand. Settled scenes stop drawing, as checked in the browser suite. Geographic geometry is memoized so scrubbing scientific time does not rebuild the scene. A/B labels use occluded SVG overlays to avoid implying a back-side point is on the visible surface.

Reduced motion and unavailable WebGL retain understandable alternatives. Responsive testing includes 1440, 1024, 768, 390, 360, and 320-pixel widths. Actual mobile behavior was checked through browser viewports; this is not equivalent to physical-device testing across every mobile browser.

### 16.3 Globe → Sky → Globe regression

The owner reported that the 3D Moon disappeared after switching from Globe to Sky and back. New tests reproduced the issue at 1440px and 390px: returning to Globe produced no canvas.

R3F intentionally loses a renderer's WebGL context during asynchronous disposal. The old context-loss listener remained attached after the view unmounted and incorrectly marked the active Explorer as failed. The correction moved that listener into a canvas-scoped lifecycle component and removed it during cleanup before renderer disposal. Cleanup also restores the pointer cursor.

Both new tests now perform five round trips, alternating immediate changes with waits for asynchronous teardown. They verify a settled returned camera, unchanged scientific UTC, and working site selection. Genuine active context loss still enters the functional fallback. Both regressions and the full 62-test browser suite pass.

This case demonstrates the value of owner feedback and targeted regression testing. It also shows why “all existing tests pass” cannot prove the absence of an interaction that the suite had not yet exercised.

## 18. Innovation, impact, and evaluation

### 18.1 What distinguishes the project

RIMWAKE's contribution is an integrated scientific interaction. The story, window comparison, exact readings, geographic context, and exports describe the same question and share a deterministic source-backed calculation.

The comparison is more useful than an isolated “Moon dashboard”: it makes a schedule change tangible and lets a reviewer follow the numerical consequence into its raw evidence. Scientific limits remain part of the result, rather than an unrelated disclaimer page. The experience combines approachability with an inspectable technical layer.

The project does not claim a new ephemeris algorithm, an independently validated terrain model, or a benchmarked advantage over professional mission-design tools. Its novelty is the design and engineering of an understandable, reproducible educational workflow around authentic data.

### 18.2 Intended impact

The intended educational impact is to help visitors distinguish place from time, Sun from Earth conditions, numerical sign from visual appearance, and sampled classifications from continuous operational availability. For educators, a reproducible link can support demonstrations and discussion. For technical reviewers, source-linked exports make scrutiny possible.

Static delivery and the absence of an account requirement reduce the components needed to access the prototype. Actual hosting costs, public reach, and long-term maintenance demand have not been established.

### 18.3 What has and has not been demonstrated

The project demonstrates working source-to-interface processing, a substantial interactive prototype, reproducible default results, and observed design refinements. Owner feedback accepted the current direction and logo.

It has not demonstrated measured learning gains, broad adoption, sustained public use, mission cost savings, safer landings, or an award outcome. Those would require separate evidence.

A useful next evaluation would ask unfamiliar users to explain the question, perform the default delay comparison, identify the active UTC, distinguish sampled geometry from operational availability, and locate the source behind a result. The planned five unfamiliar-user sessions have not yet been conducted. Completion rate, time to the first correct comparison, explanation accuracy, and evidence-finding success are proposed evaluation measures, not current impact statistics.

## 19. Limitations and future development

| Area | Present limitation | Appropriate next work |
|---|---|---|
| Scientific validation | Source consistency is checked; independent model validation is open | Independent reference calculations and documented tolerances |
| Reference frames | Catalog/Horizons equivalence is not independently reconciled | Explicit coordinate-frame reconciliation |
| Sampling | Hourly atlas can miss changes between endpoints | Scientifically justified refinement with retained provenance |
| Terrain | No DEM skyline or local obstruction calculation | Separately validated terrain pipeline and observer geometry |
| Physical availability | No finite discs, eclipses, power, or RF model | Clearly scoped, separately validated extensions |
| Performance | First verified Explorer result and normal 3D payload miss targets | Reduce measured startup/payload costs and retest |
| Usability | No unfamiliar-user study | Structured comprehension/task sessions |
| Accessibility | Automated checks are bounded | Manual keyboard, screen-reader, zoom, and device assessment |
| Browser coverage | Retained automation uses installed Chrome | Additional browser and physical-device checks |
| Publication | Local checks do not prove production delivery | Authorized deployment, anonymous-access checks, and receipts |

Advanced terrain work remains a scientifically gated extension requiring explicit owner approval after a stable deployed P0. Rendering a realistic Moon is not sufficient evidence for terrain calculations. A future terrain model would need documented resolution, vertical datum, observer height, coordinate transformations, horizon extraction, and validation.

The existing prototype should remain recoverable while extensions are developed. New source acquisitions should be versioned as new scientific releases rather than silently replacing a published archive under the same identity.
